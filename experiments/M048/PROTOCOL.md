# M048 — genuine native runtime migration with post-migration learning

**Status: IN DEVELOPMENT.**

## Why M048 exists

M047 established a bounded continuing lineage whose mutable organism is a real executable
modular Python application. M048 asks the next direct question: can the same lineage preserve
its acquired body, tests, tools, memory and causal reasons while moving to a genuinely
different runtime, then diagnose and learn a new capability after the source runtime has been
removed from the execution path?

M048 is one integrated migration experiment. It is not a sequence of new substrate gates and
it does not requalify the M047 module architecture.

## Fixed source and target runtimes

- source runtime: CPython;
- target runtime: Node.js using native ECMAScript modules;
- source lineage state: exact reconstructed M047 accepted version six;
- migrated lineage version: seven;
- accepted post-migration learning version: eight;
- forced-fault provisional version: nine.

The migrated body must execute without importing, invoking or delegating semantics to Python.
A Python controller may launch an isolated Node process and verify its artifacts, but the
accepted body semantics, proposal execution and hidden validation all run in Node.

## Migrated body

The M047 version-six body contains nine executable modules:

- interpretation;
- planning;
- selection;
- execution;
- critique;
- allocation;
- orchestration;
- core arithmetic tools;
- the acquired `mean` tool.

M048 compiles their accepted metadata and behaviour into nine native ESM modules. The native
state also preserves:

- the exact M047 source snapshot identity;
- six inherited patch-tool records;
- six inherited accepted task identities;
- the inherited hash-chained causal journal;
- inherited causal success and failure memory;
- twelve generated regression cases;
- twelve retained validator-only hidden cases;
- four founder baseline cases;
- the causal reason and digest of migration.

The migration is accepted only when all twenty-eight retained capabilities pass inside the
Node runtime and the previously acquired `mean` tool is observed in the native execution
trace of a pre-migration capability.

## Independent native roles

The integrated experiment uses separate Node processes for three roles:

1. **execution** — load the accepted ESM body and execute cases;
2. **proposal** — receive only the accepted native body and public cases, diagnose the
   limiting boundary and generate a bounded candidate set;
3. **validation** — receive retained, public and hidden cases and decide whether a candidate
   earns release authority.

The proposal process never receives hidden cases. The validator cannot modify the accepted
state. Only its accepted selection artifact may enter the Python-held transactional lineage
store.

## Post-migration learning task

After migration, the native body faces the unseen public token `maximum`.

The proposal process must diagnose an interpretation failure and construct bounded composite
native candidates that may:

- extend the interpreter alias map;
- extend native tool selection;
- create a new executable `tool_max` ESM module;
- add native regression cases.

The candidate family contains four fixed expression hypotheses: maximum, minimum, sum and
midpoint. It is a tiny bounded proposal surface and explicitly does not enumerate JavaScript
programs, source strings or the complete candidate space.

A separate hidden validator admits only the candidate that preserves every inherited
capability and passes all public and hidden `maximum` cases. Successful adoption creates
version eight and must retain the acquired pre-migration `mean` tool.

## Forced rollback

At version eight the native body faces `largest`, which can reuse the acquired native `max`
capability through an interpreter alias patch. The candidate is independently validated, but
causal-journal corruption is forced during provisional version-nine adoption.

The audit must detect that the latest journal entry no longer binds the latest patch record,
validation artifact and accepted executable body. The lineage must restore the exact
version-eight body, registry, journal, memory and checkpoint bytes.

## Insufficient-evidence terminal task

The restored native body then faces `median`. Public symmetric triples permit an alias to
`mean` to appear plausible, while hidden asymmetric triples distinguish median from mean.
All bounded candidates must be independently rejected.

The lineage must:

- terminate explicitly for insufficient evidence;
- preserve the accepted version-eight body;
- retain the rejection evidence in causal memory;
- avoid widening the proposal surface after observing hidden failures.

## Fixed resources

- generated native candidates per task: `8` maximum;
- independently validated candidates per task: `4` maximum;
- complete native body: `131,072` bytes maximum;
- Node process timeout: `30` seconds;
- post-migration accepted cycles: exactly `1`;
- complete candidate-space enumeration: forbidden;
- repository, network, credential and deployment authority: absent.

## Replay

M048 replays artifacts rather than rerunning discovery to replace a result. It must:

1. reconstruct the same M047 version-six source lineage;
2. compile the same native version-seven body;
3. adopt the recorded independently validated `maximum` candidate;
4. repeat the forced version-nine rollback;
5. append the recorded `median` failure episode;
6. reproduce the exact final native state digest.

## Success criteria

M048 passes in development only if permanent falsification tests establish:

- exact continuity from M047 version six;
- genuine CPython-to-Node ESM migration;
- no Python semantic delegation in the migrated body;
- all twenty-eight inherited capabilities preserved;
- pre-migration `mean` tool observed in a post-migration execution trace;
- bounded non-exhaustive native proposal;
- independent Node hidden validation;
- creation of a new executable `tool_max` module;
- native source and test adoption at version eight;
- preservation of all inherited capabilities after learning;
- exact forced-fault rollback from provisional version nine to version eight;
- explicit insufficient-evidence termination on `median`;
- rejection evidence retained without body adoption;
- exact migration and post-migration replay;
- bounded, noncanonical claim metadata.

## Claim boundary

M048 is a bounded development experiment over one fixed Python body architecture, one fixed
metadata compiler, one fixed Node ESM runtime and fixed task families. It does not establish
arbitrary language translation, unknown-runtime discovery, unrestricted native code
synthesis, open-ended evolution, general intelligence, consciousness or production safety.

M048 selects no seed, freezes no canonical hidden bank and authorises no canonical workflow.
M042 remains the only positive canonical continuous-lineage completion. M045 remains the
separate proxy-measurement track.
