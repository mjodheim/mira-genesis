# M093 — first real persistent component transformation

**Status: transformation experiment completed, patch adopted. Engineering rehearsal / non-qualifying development result.**

This experiment is deliberately the smallest credible one: it creates no new architecture. It reuses mechanisms already present in the repository — subprocess sandbox (M047 pattern), transactional adoption and exact rollback (M047 pattern), independent validation (M047 pattern) — and applies them to a **real component used by Genesis**: `mira_core/memory.py` (`MemoryLedger`).

## Authored elements (non-qualifying)

The following elements are authored, making this an engineering rehearsal rather than a qualifying scientific self-rewrite experiment:

- `TARGET_FILE = "mira_core/memory.py"` — the component was hand-chosen, not diagnosed by Genesis
- `missing_events_by_kind_method` — the insufficiency was identified by a human, not discovered by the lineage
- `events_by_kind` capability choice — the required method name and signature are authored
- `CodePatch.generate` — the exact patch code is authored, not generated from a specification
- Candidate test suite — the sandbox assertions are authored
- Held-out validator — the validator and its suite are authored; the validator is too close to the generator to support a strong isolation claim
- Comparison criterion — the A/B comparison rule is authored
- End-of-experiment re-adoption — the patch is explicitly re-adopted at the end of the experiment

## What M093 actually demonstrates

The project now possesses infrastructure capable of:

- transforming a real repository component
- testing the original and candidate in isolated subprocess sandboxes
- performing an objective A/B comparison
- validating through a separate held-out suite
- adopting the candidate through a transactional body mechanism
- persisting the state to disk and verifying digest integrity after simulated restart
- performing an exact byte-identical rollback of the original

M093 does **not** demonstrate that Genesis autonomously discovered the limitation, chose the component, or generated a non-predefined repair.

## Recognised insufficiency

`MemoryLedger` exposes no declarative way to retrieve events by kind. Each consumer must write `tuple(e for e in ledger.events if e.kind == ...)` themselves. Measured proof: the component has no query method by `kind`.

## Modification produced

Addition of a public `events_by_kind(kind)` method to `MemoryLedger`: deterministic filter, insertion-order-preserving, empty-kind rejection, no mutation of the registry, compatible with checkpoint/restore and with the digest chain (tamper-evidence intact).

## Pre-defined criterion

H0: no measurable difference between original and candidate on the criterion "all assertions pass and the candidate adds the capability to query by kind". H0 is rejected only if the original **and** the candidate pass their full sandbox suites.
