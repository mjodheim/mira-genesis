# M041 — frozen isolated single-lineage completion protocol

**Status: frozen pre-result protocol.** No canonical seed, task or M041 outcome exists until
the unique marker-only arming commit is immutable. No rule below may change afterward.

## Bounded target claim

One deterministic lineage must satisfy all ten gates in `GENESIS_COMPLETION_CRITERIA.md`:
identify a structural limitation, own and reuse a constructed rewrite tool, generate and adopt
an exact improvement, validate the candidate behind an independent fail-closed boundary,
migrate its competence and plastic state to an initially opaque substrate, improve there on a
new hidden task, survive rollback, complete repeated cycles and reproduce the whole result from
sealed immutable inputs.

The claim is restricted to the frozen deterministic binary-DFA and opaque Boolean-machine
families. It is not a claim of arbitrary code safety, open-ended evolution, general
intelligence, consciousness or permission to modify external systems.

## Frozen lineage mechanism

The canonical runner executes a fresh M040-style cumulative lineage using:

- a master seed derived only after the marker-only M041 arming commit exists;
- the M041 protocol SHA-256 as the underlying lineage commitment;
- the frozen `lineage_anchor` post-migration family;
- complete seed-only replay;
- the M041 isolated validator hook before the post-migration `CandidateAdopted` event.

M040 canonical identities and artefacts remain immutable historical evidence. M041 regenerates
a new lineage from its own sealed seed; it does not reuse the M040 canonical result or the
consumed M041 development seed.

## Frozen isolated-validation boundary

The proposal is passive canonical DFA data, not executable candidate source. A fixed trusted
runner executes in a fresh temporary subprocess workspace before M041 release adoption.

Limits:

- CPU: 2 seconds;
- address-space memory: 134,217,728 bytes;
- output file size: 2,097,152 bytes;
- process count: 1;
- open file descriptors: 32;
- wall time: 5 seconds;
- captured output: 131,072 bytes;
- maximum DFA states: 64;
- maximum observations: 4,096;
- maximum serialised input: 4,194,304 bytes.

The candidate has zero code, import, dynamic-execution, network, syscall-selection or
filesystem-write authority. The fixed runner may perform only its committed local reads,
finite DFA traversal and result write to standard output. This is a passive-data isolation
boundary, not a general container or micro-VM claim.

Before adoption, the workspace independently verifies:

1. canonical DFA schema and dimensions;
2. structural limits and transitions;
3. candidate digest;
4. exact committed case digest;
5. all 127 hidden-task observations;
6. every critical regression where parent and target agree;
7. strict observed improvement over the parent;
8. exact language equivalence with the hidden target;
9. deterministic byte-identical result under seed-only replay.

Any malformed data, timeout, resource failure, digest mismatch, omitted or reordered case,
regression failure, stale parent, non-exact candidate or malformed runner output rejects
adoption and leaves the release body unchanged.

## Frozen gate decision rule

### Gate 1 — autonomous diagnosis

Supported only if the post-migration structural certificate is independently recomputable,
available and proves a minimum state count greater than the migrated parent. The diagnosis
must precede candidate adoption and no fault location or repair arguments may be supplied.

### Gate 2 — internal tool ownership

Supported only if the accepted post-migration proposal causally uses a lineage-owned tool
constructed from primitives during the same lineage before migration, and the equal-budget
tool ablation fails exact solution.

### Gate 3 — self-rewrite

Supported only if the accepted candidate differs from the parent, has a committed
transformation trace and is exactly replayable from the parent.

### Gate 4 — isolated validation

Supported only if both the first execution and seed-only replay pass the frozen passive-data
workspace before adoption, produce identical validation and workspace identities, and all
failure controls remain fail-closed.

### Gate 5 — held-out improvement

Supported only if the complete lineage reaches 127/127 on the hidden post-migration task,
preserves every critical regression, beats the unchanged parent and declared controls under
equal budgets, and the same lineage has already completed the three exact pre-migration hidden
improvement cycles. All diagnosis, search, rejected candidates, validation and migration costs
remain separately reported.

### Gate 6 — adoption and rollback

Supported only if adoption occurs after isolated validation, the parent is archived exactly,
and the forced bad provisional source/native pair rolls back to the accepted pair exactly.

### Gate 7 — complete trans-substrate metamorphosis

Supported only if substrate semantics are discovered by probing, the improved competence,
tool registry and causal learning state migrate exactly, and post-migration source/native
bodies remain equivalent.

### Gate 8 — post-migration plasticity

Supported only if the complete migrated lineage solves exactly and is strictly better under
the equal frozen comparison than fresh-on-B, unchanged-parent, output-only,
learning-state-ablated and learned-tool-ablated controls according to the frozen M040 rule.

### Gate 9 — repeated improvement cycles

Supported only if one lineage completes the three exact pre-migration cycles and the exact
post-migration rewrite, reuses a tool from an earlier cycle and reproduces all search histories
from the original sealed seed.

### Gate 10 — measurement integrity

Supported only if this protocol and mechanism are committed before the task seed exists, the
canonical workflow opens on exactly one marker-only commit, the first scientific result is
preserved regardless of sign, and no later rerun, threshold change or replacement seed alters
that result.

The combined bounded Genesis completion claim is supported only when all ten gates are true.
Any single false gate makes the combined result negative while preserving the individual gate
verdicts.

## Sealed seed derivation

Importing the sealed module derives nothing. After the marker-only arming head exists:

1. compute the master nonce from the arming-head SHA and frozen protocol SHA-256 under the
   `m041:sealed-head` domain;
2. derive the canonical task seed under label `completion`, index zero;
3. derive all lineage, substrate and task sub-seeds only through the committed M040 mechanism.

The seed cannot be calculated before the immutable arming commit.

## Integrity and release boundary

The unique canonical workflow accepts only a commit that changes
`experiments/M041/CANONICAL_ARMED.json` and carries the exact arming message. A negative
scientific outcome is a successful workflow execution and must be preserved.

Even a positive completion result remains inside a sandboxed research laboratory. Repository
writes, deployments, credentials, network operations and production changes remain behind an
explicit human-controlled release boundary.
